Introduction

A database is used to store and manage information in a structured and reliable manner. In a college database, student details, department information, email addresses and marks must remain accurate and consistent.

Without proper rules, a database may contain duplicate Student IDs, invalid Department IDs, NULL values in mandatory fields, duplicate email addresses or marks outside the valid range of 0–100. These are known as database integrity violations.

2. SQL Constraints: Solutions and Justifications

PRIMARY KEY

Preventing Duplicate Student IDs

A Student ID uniquely identifies a student, so it is the appropriate candidate for a primary key. A primary key cannot contain duplicate or NULL values. 

Student_ID VARCHAR(10) PRIMARY KEY
If omitted: duplicate records could be stored, and it would become difficult to identify, update or delete a particular student reliably.
FOREIGN KEY

Preventing Invalid Department IDs

Department_ID in Student should refer to a valid Department_ID in the Department table. This keeps the relationship between the two tables consistent. 

FOREIGN KEY (Department_ID)
REFERENCES Department(Department_ID)
If omitted: students could be assigned to departments that do not exist, creating invalid references.
NOT NULL

Preventing Missing Mandatory Information

Required information such as Student Name, Department ID and Email should always have a value. 

Student_Name VARCHAR(100) NOT NULL,
Department_ID VARCHAR(10) NOT NULL,
Email VARCHAR(100) NOT NULL
If omitted: incomplete records could be stored, making reports and searches less reliable.
UNIQUE

Preventing Duplicate Email Addresses

A student's email address should be unique when it is used as a login, communication or account identifier. 

Email VARCHAR(100) NOT NULL UNIQUE
If omitted: multiple accounts could use the same email.
CHECK

Keeping Marks Between 0 and 100

The CHECK constraint enforces the rule that valid marks must satisfy 0 ≤ Marks ≤ 100. 

Marks INT CHECK (Marks >= 0 AND Marks <= 100)
If omitted: values such as -10, 105 or 150 could be stored.

3. Referential Actions

Referential actions determine what happens to related Student records when a referenced Department record is deleted or changed.

🛑 RESTRICT

Prevents deletion of a department while dependent student records exist. 

ON DELETE RESTRICT

Recommended when: student records must be preserved.

⚡ CASCADE

Automatically deletes dependent student records when the referenced department is deleted. 

ON DELETE CASCADE

Risk: deleting one department could unintentionally delete all associated students.

↪ SET NULL

Leaves the student record but removes its department relationship by setting Department_ID to NULL. 

ON DELETE SET NULL

Requirement: Department_ID must allow NULL.

Recommended choice for this college example: ON DELETE RESTRICT is generally the safest option when student academic records must not be accidentally deleted.

5. Complete SQL Implementation

Department Table 

CREATE TABLE Department (
    Department_ID VARCHAR(10) PRIMARY KEY,
    Department_Name VARCHAR(100) NOT NULL UNIQUE
);

Insert Department Records 

INSERT INTO Department (Department_ID, Department_Name)
VALUES
('D01', 'Information Technology'),
('D02', 'Computer Engineering'),
('D03', 'Electronics Engineering');

Student Table 

CREATE TABLE Student (
    Student_ID VARCHAR(10) PRIMARY KEY,
    Student_Name VARCHAR(100) NOT NULL,
    Department_ID VARCHAR(10) NOT NULL,
    Email VARCHAR(100) NOT NULL UNIQUE,
    Marks INT CHECK (Marks >= 0 AND Marks <= 100),

    FOREIGN KEY (Department_ID)
        REFERENCES Department(Department_ID)
        ON DELETE RESTRICT
);

Valid Student Records

Examples of Invalid Data 

-- 1. Duplicate Student ID → PRIMARY KEY rejects it

INSERT INTO Student
VALUES ('S101', 'Amit', 'D01', 'amit@email.com', 80);


-- 2. Invalid Department → FOREIGN KEY rejects it

INSERT INTO Student
VALUES ('S106', 'Karan', 'D99', 'karan@email.com', 80);


-- 3. Missing Name → NOT NULL rejects it

INSERT INTO Student
VALUES ('S107', NULL, 'D01', 'student@email.com', 80);


-- 4. Duplicate Email → UNIQUE rejects it

INSERT INTO Student
VALUES ('S108', 'Rohan', 'D01', 'priya@email.com', 80);


-- 5. Invalid Marks → CHECK rejects it

INSERT INTO Student
VALUES ('S109', 'Neha', 'D01', 'neha@email.com', 105);

6. Constraint Comparison

Invalid Department IDs FOREIGN KEY Maintains valid relationships Invalid references
NULL in mandatory fields NOT NULL Requires essential values Incomplete records
Duplicate email addresses UNIQUE Prevents repeated emails Duplicate accounts
Marks outside 0–100 CHECK Enforces valid marks Incorrect marks
Department deletion/update Referential Action Controls related records Inconsistency or accidental deletion

Conclusion

Database integrity is essential for maintaining accurate, reliable and consistent college records.

The PRIMARY KEY prevents duplicate Student IDs and uniquely identifies students. The FOREIGN KEY prevents invalid Department IDs and maintains relationships between tables. The NOT NULL constraint ensures mandatory information is present.

The UNIQUE constraint prevents duplicate email addresses, while the CHECK constraint ensures marks remain within 0–100.

Referential actions such as RESTRICT, CASCADE and SET NULL control how changes to parent records affect related records. For the college example, RESTRICT is generally a safe choice when student records must be preserved.

Final takeaway: Properly selected SQL constraints act as a first line of defense against incorrect, duplicate and inconsistent data, making the college database more reliable and maintainable.
